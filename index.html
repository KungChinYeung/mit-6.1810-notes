01 — Overview

A layer of software

The topic of this course is a layer of software that sits below applications and above the hardware. The operating system multiplexes the hardware, keeps applications from stepping on one another, lets them share, and hides the messy details of the machine behind clean abstractions.

Multiplex

Share one machine among many applications at once.

Isolate

Contain bugs and provide security between apps.

Share

Let cooperating applications exchange data.

Abstract

Hide the hardware for portability and convenience.

Design is hard: the constraints conflict

An O/S must simultaneously satisfy goals that pull in different directions. Every design decision is a trade-off:

Performance Generality Power Security

Why take this course

  • Satisfy curiosity about the inner workings of computers.
  • Get better at tracking down bugs.
  • Understand and reason about performance.

04 — The O/S model

User space, kernel, hardware

A standard picture of an operating system. Applications live in user space; the kernel provides services — file system, processes, memory, network — and exposes them through system calls.

user space
Applications
shell · echo · ls · your programs
system calls
kernel
Kernel (O/S)
file system processes memory network
Hardware
RISC-V CPU · memory · disk · devices

User space. Untrusted, isolated processes.

Kernel. Privileged, trusted code.

Hardware. Managed by the kernel.

What happens on a system call?

It looks like a function call, but it is actually a carefully choreographed transition into the kernel and back:

  1. 1

    User code calls read()

    An ordinary-looking call in the program.

  2. 2

    A special instruction traps into the kernel

    The CPU saves some user registers, raises the privilege level, and jumps to a known entry point.

  3. 3

    Kernel C code runs the implementation

    e.g. sys_open() looks up a name, maybe waits for the disk, and updates kernel data structures (block cache, FD table).

  4. 4

    Return to the program

    Restore user registers, drop the privilege level, and resume right after the call.

05 — System-call examples

Nine tiny programs

Running on xv6 — a much-simplified UNIX, small enough to read and understand completely. These examples show the core system calls; the shell itself is built from the very same pieces.

ex1

Copy input to output

Read bytes from input and write them to output. read() and write() are system calls: they look like function calls but actually jump into the kernel, preserving user/kernel isolation. The first argument is a file descriptor (FD); by UNIX convention FD 0 is standard input and FD 1 is standard output.

ex1.c
read(fd, buf, n) — may read fewer bytes, never more; returns the count or −1.
8-bit bytes. The kernel doesn't care about format; interpretation is the app's job.
ex2

Create a file

open() creates or opens a file on disk and returns a small integer FD (or −1 on error). The FD indexes into a per-process table maintained by the kernel, so different processes have different FD namespaces — FD 3 usually means different things to different processes.

ex2.c

These examples ignore errors — don't be this sloppy! Figure 1.2 of the xv6 book lists the system calls, or see man 2 open.

ex3

Create a new process with fork()

A process is a running program with memory, a stack, and kernel state, isolated from other processes to contain bugs. fork() creates a new process by copying the caller — instructions, data, registers, FDs, current directory. Parent and child are initially identical, except fork() returns a pid in the parent and 0 in the child.

ex3.c

Both processes continue after the fork — the if (pid == 0) test is how each learns which one it is.

ex4

Replace the process with exec()

To run a program such as echo, the shell needs another mechanism. exec(filename, argv) replaces the current process with an executable file: it discards the old instruction and data memory, loads the new program, and preserves file descriptors. exec() does not return if it succeeds.

ex4.c
echo.c — how a program reads its argv
ex5

fork() then exec(), and wait()

The shell can't simply call exec() — it would no longer be running and couldn't accept another command. Instead it forks a child, the child execs, and the parent wait()s for the child to finish. The shell does this fork / exec / wait for every command you type. exit(status) pairs with wait(&status), passing back 32 bits; by convention 0 means success.

ex5.c

Note the seeming waste: fork() copies memory that exec() immediately discards. You'll eliminate that in the copy-on-write lab.

ex6

Redirect the output of a command

How does the shell implement echo hello > out? Fork, then the child changes FD 1 before exec'ing echo. open() always chooses the lowest unused FD — here 1, because the child first close(1)s it. Because exec() preserves FDs, the new program writes to the file without knowing it.

ex6.c

FDs provide indirection: commands just use FDs 0 and 1, so only the shell needs to know about redirection.

ex7

Communicate through a pipe

An FD can refer to a pipe instead of a file. The pipe() call creates two FDs: read from the first, write to the second. The kernel keeps a buffer for each pipe; write() appends to it and read() waits until data is available.

ex7.c
ex8

Communicate between processes

Pipes combine with fork() so a parent and child can communicate: create a pipe, fork, then the parent writes to one pipe FD while the child reads from the other. The shell builds pipelines like ls | grep x from exactly these pieces.

ex8.c
ex9

List files in a directory

How does ls get the files in a directory? You can open() a directory and read() it, yielding file names. Here "." is a pseudo-name for the process's current directory.

06 — Other designs

The UNIX choices aren't the only ones

Names instead of FDs

Pass a filename to read()/write() rather than an FD.

No file system

Access the disk directly instead of through a file system.

Combine fork & exec

A single call that both creates and runs a program.
